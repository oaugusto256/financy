## Detail

### 1. Nothing mechanically enforces the gate, and it has already been missed once

**Evidence:** No `.github/` directory and no other CI config. No `husky`,
`lint-staged` or `simple-git-hooks`; `.git/hooks/` holds only `*.sample` files.
The root `package.json` has no aggregate `codegen:check`, so the gate is six
commands in two invocation shapes. Commit `5cd82a6` ("style: format the category
model test", PR #5) is a pure Prettier re-wrap — a `format:check` failure caught
only after the fact, matching `CLAUDE.md:99-100`.

**Cost:** All five slices landed on `main` with no independent verification.
The only thing between a broken commit and `main` is a person remembering six
commands and transcribing the output into a PR body. That already failed once.

**Fix:** Three steps, one commit, no source change. Add a root `verify` script
chaining the six commands; add `.github/workflows/ci.yml` running it on
`pull_request`; add `simple-git-hooks` + `lint-staged` running `prettier --check`
and `eslint --max-warnings 0` on staged files. Point the README's "Verifying it"
section at `verify`. Effort: S.

### 2. A one-character `JWT_SECRET` passes boot validation

**Evidence:** `backend/src/shared/env.ts:5` — `z.string().min(1)` is the only
constraint. `backend/src/shared/jwt.ts:4-5` feeds it straight into an HS256 HMAC
key. `backend/.env.example:2` ships `JWT_SECRET=` with no stated minimum. The
agent booted the real app with `JWT_SECRET="x"` and it started and issued a
working token. `backend/tests/unit/env.test.ts:34-42` tests only missing and
empty.

**Cost:** A short HS256 key is recovered offline from one captured token in
seconds. The attacker gets a token by signing up. With the key they can mint a
token for any `sub` — the only thing standing in the way is that `sub` is a uuid
that the API never publishes, which is an accident of the id format, not a
control. The repo cannot tell you whether the deployed secret is weak; the
finding is that nothing stops it from being.

**Fix:** `z.string().min(32, …)` in `env.ts`, the expectation as a comment in
`.env.example`, the negative case in `env.test.ts`. Rotate whatever is deployed.
Effort: S.

### 3. No React error boundary — a render throw blanks the app silently

**Evidence:** `frontend/src/App.tsx:16-28` — the tree is
`QueryClientProvider > ToastProvider > BrowserRouter > SessionProvider > AppRoutes`
with no boundary. `frontend/src/routes.tsx:32-53` wraps no route either.
`grep -rln "ErrorBoundary\|componentDidCatch" frontend/src` — zero matches.

**Cost:** React unmounts the whole tree on an uncaught render exception. Any
single component bug takes the app to a blank white page with no fallback and
no report. Row 6 is exactly the drift that would trigger it — a response shape
the frontend did not expect, with no safety net.

**Fix:** A top-level `ErrorBoundary` around `<AppRoutes />` rendering a
Portuguese fallback, reporting the caught error. One test asserting the fallback
renders instead of nothing. Effort: S.

### 4. No backend error observability, and Apollo's production posture is unpinned

**Merged from `test-01` and `sec-04` — same file, same fix, two halves of one
problem.** Severity taken from the higher of the two.

**Evidence:** `backend/src/app.ts:16` constructs `ApolloServer` with only
`typeDefs` and `resolvers` — no `formatError`, no `plugins`, no `introspection`,
no `includeStacktraceInErrorResponses`. `backend/src/server.ts:7` is the only
`console.*` under `backend/src`; there is no logging library and no per-request
line. Apollo reads `process.env.NODE_ENV` **directly**
(`@apollo/server/dist/esm/ApolloServer.js:30,33,62`), not the app's validated
`env`, and `backend/src/shared/env.ts:8-10` declares `NODE_ENV` with
`.default('development')` — optional. The agent booted with `env -u NODE_ENV`:
introspection served, 33 types, and every error carried
`extensions.stacktrace` with absolute host paths. Apollo 4 does not mask
unexpected error messages either
(`errorNormalize.js:5,52-57`) — confirmed by row 11's transcript, where a
graphql-js internal message reached an unprivileged client.

**Cost:** Two things at once. A resolver throw is recorded nowhere the owner can
read — not which user, not which operation, not that it happened; an incident
cannot be reconstructed. And a deploy that omits `NODE_ENV=production` — which
this app's own env contract says is optional — publishes its full schema and
returns host paths and `node_modules` layout in every error. With row 16, a
Prisma `P2002` reaches the client naming the table and column.

**Fix:** In `app.ts`, drive Apollo from the validated env:
`introspection: env.NODE_ENV !== 'production'`,
`includeStacktraceInErrorResponses: env.NODE_ENV === 'development'`, and a
`formatError` passing through the five codes in `shared/errors.ts:4-10` and
replacing anything else with a fixed message. Add a `didEncounterErrors` plugin
logging operation name, `context.userId` and the error. Consider making
`NODE_ENV` required. One integration test asserting no stack trace escapes.
Effort: M.

### 5. Nothing rate-limits `signIn` or `signUp`

**Evidence:** `backend/src/app.ts:21-31` — the `/graphql` chain is `cors`,
`express.json`, `expressMiddleware`. No limiter, no lockout, no
`express-rate-limit`, no `helmet` in the dependency tree. No `failedAttempts` or
`lockedUntil` column exists to hold state. Live: 50 sequential failed sign-ins
against one account answered in 751 ms, no 429 — ~66 guesses/second serially,
and argon2 runs on the libuv threadpool so parallel connections multiply it.

Two things checked so the fix is not aimed wrong: alias amplification does **not**
work (200 aliased `signIn` mutations in one POST produced exactly one attempt,
because the field is non-null and the first error halts serial execution — a real
but accidental defence that evaporates if the field becomes nullable), and
`express.json()`'s 100 kB default bounds one request's size, not the request rate.

**Cost:** With row 7 an attacker first confirms which addresses have accounts,
then grinds them unbounded. The password floor is eight characters with no
composition rule, so stuffing lists work. `signUp` is equally unbounded and each
call costs a 19 MiB argon2 hash plus a row — a memory-pressure and disk-growth
vector against a single-file SQLite database.

**Fix:** `express-rate-limit` ahead of `expressMiddleware`, keyed on IP, plus a
tighter limiter keyed on the submitted email for `signIn`/`signUp` — a per-IP
limit alone is defeated by a botnet spraying one guess per address. Limits into
`.env.example` and `env.ts` if configurable. One integration test. Effort: M.

### 6. MSW fixtures are never type-checked against the schema, at 105 call sites

**Evidence:** `msw`'s `GraphQLRequestHandler` is generic over `Query`/`Variables`
and falls back to untyped defaults when no argument is given.
`grep -rn "api\.\(query\|mutation\)<" frontend/src` — 0 matches;
the same grep with `(` — 105. The schema-accurate generated types exist
(`frontend/src/graphql/generated/graphql.ts:228,234,239` and equivalents) and no
call site references them. `codegen:check` diffs only
`src/graphql/generated` against `graphql/operations/*.graphql` — it never reads
`src/test/msw/api.ts` or any test file.

**Cost:** Every mock happens to match the schema today — the agent compared them
by hand and found no live mismatch. Nothing enforces it going forward. Renaming
a field, changing a nullability or renaming an enum value would fail neither
`typecheck`, `lint` nor `codegen:check` on the test side: the mocks keep
returning the old shape and 324 green frontend tests certify a response the real
backend can no longer produce.

**Fix:** Type every call with its generated operation type, and tighten the
`ok`/`graphqlError` helper generics in `frontend/src/test/msw/api.ts:10-14`
(currently `T extends Record<string, unknown>`, which accepts anything).
Mechanical but touches every test file with a handler — a codemod, not manual
edits. Effort: L.

### 7. `signIn` leaks account existence through a 24× response-time gap

**Evidence:** `backend/src/modules/auth/service.ts:38-45` — the unknown-email
branch returns before argon2 runs. Measured: one argon2 verify is 13–14 ms
(`$argon2id$v=19$m=19456,t=2,p=1`); over real HTTP, median `signIn` is 14.3 ms
for an existing address and 0.6 ms for an unknown one. The comment at lines
39-41 claims the branches are equivalent — true of the error code, and precisely
why the timings differ.

**Stated honestly:** enumeration is already possible more cheaply and by design —
`signUp` answers `EMAIL_ALREADY_EXISTS` on a taken address, a deliberate product
decision recorded in `docs/specs/backend.md` §7 and rendered by the frontend.
Closing the timing channel does not close enumeration. It is still worth fixing:
this channel is the one that is not intentional, and its comment currently
claims a property the code does not have.

**Fix:** Hash a module-level dummy argon2 encoding on the `!user` branch so both
paths pay the same cost, then throw. Correct the comment to say what is and is
not equalised. Effort: S.

### 8. Error codes are a cross-workspace contract, typed on one side only

**Evidence:** `backend/src/shared/errors.ts:4-10` — `ErrorCode` as a typed
`as const` object whose comment reads "The frontend switches on these."
`frontend/src/lib/graphql-errors.ts:4` — `errorCodeOf` returns
`string | null`; there is no union type for the codes anywhere in `frontend/`.
Three comparisons against bare literals: `graphql-client.ts:15`
(`'UNAUTHENTICATED'`), `LoginPage.tsx:39` (`'INVALID_CREDENTIALS'`),
`SignUpPage.tsx:35` (`'EMAIL_ALREADY_EXISTS'`). The codes are not GraphQL enums,
so neither codegen run carries them across the boundary.

**Cost:** A backend rename leaves all three comparisons compiling and silently
false, with no frontend test failing. `UNAUTHENTICATED` is the worst: it triggers
`notifyUnauthenticated()`, so an expired token would stop redirecting to login
and leave the user on a screen of failed panels — the exact outcome
`docs/specs/frontend.md:325-328` says must not happen. Separately, `NOT_FOUND` is
handled nowhere on the frontend, so deleting a row a second tab already deleted
renders "Não foi possível excluir. Tente novamente." — a retry prompt for an
operation that can never succeed.

**Fix:** Declare `export type ErrorCode = …` in `graphql-errors.ts` and return
`ErrorCode | null`. That collapses three copies to one and makes a typo a compile
error. It does **not** close the cross-workspace gap — a backend rename still
compiles on both sides. Closing that means promoting the codes to an SDL enum so
codegen emits them. Effort: S for the frontend side, L for the real fix.

### 9. `/health` never touches the database, and the route a monitor would hit is untested

**Evidence:** `backend/src/app.ts:33-35` — `GET /health` returns
`{ status: 'ok' }` unconditionally, no Prisma call. `backend/src/schema.ts:18,40`
— a second, separate surface, `Query.health: String!`, also unconditional.
`backend/tests/integration/health.test.ts:20-27` posts `{ query: '{ health }' }`
to `/graphql`; `grep -rn "'/health'" backend/tests backend/src` finds only the
route definition. Nothing ever issues `GET /health`.

**Cost:** Whatever monitors this service most plausibly polls the REST route —
the conventional path — which is both untested and green regardless of whether
SQLite is reachable. A database outage leaving every real query failing still
shows healthy, and no test would catch a regression to the route either way.

**Fix:** Probe the database (`prisma.$queryRaw\`SELECT 1\``, the same call
`backend/tests/integration/prisma.test.ts` already uses), return 503 on failure,
and add a `supertest` test for both the healthy and broken-connection cases.
Effort: S.

### 10. The declared Node floor is lower than the toolchain actually runs on

**Evidence:** root `package.json:8-10` — `"node": ">=20"`, with no `.nvmrc` or
`.tool-versions`. `README.md:12` repeats "Node 20 or newer". Installed
`vite@8.2.0` declares `"node": "^20.19.0 || >=22.12.0"`. `backend/package.json:6`
and `:17` invoke `tsx --env-file-if-exists=.env`, a flag that did not exist
before Node v20.19.0. Both constraints converge on the same real floor: 20.19.0.

**Cost:** A contributor who installs "Node 20" literally — an LTS point release
before 20.19.0, satisfying `>=20` and matching the README's own instruction —
gets a working `npm install` and then a crash on `npm run dev -w backend` from
an unrecognized flag. The stated minimum does not run the stated dev command.

**Fix:** `engines.node` → `"^20.19.0 || >=22.12.0"`, add `.nvmrc`, correct
`README.md:12`. Effort: S.

### 11. Two transactions at the `Int` ceiling permanently break the `summary` query

**Evidence:** `backend/src/modules/transaction/validation.ts:26-28` — `amount` is
`z.int().positive()`, lower bound only. `schema.prisma:39` stores it as SQLite
`INTEGER` (64-bit), so the database holds the sum happily.
`backend/src/modules/summary/service.ts:66-70` returns the raw `groupBy` sums and
`schema.graphql` declares all three `Int!`. End to end: two `createTransaction`
mutations at `amount: 2147483647` were both accepted, then `summary` returned
`Int cannot represent non 32-bit signed integer value: 4294967294` with
`path: ["summary","totalBalance"]`. `frontend/src/lib/currency.ts:9,41` knows the
ceiling and clamps; the backend does not.

**Cost:** `totalBalance` is non-null, so the error nulls the whole `summary`
field: the dashboard returns `data: null` for every month until the offending
rows are deleted, and the error message says nothing about which. Three amounts
of R$ 8.000.000,00 also do it — not absurd for a business account in BRL. The
spec is silent on the ceiling, so `docs/specs/backend.md` §5 needs correcting in
the same PR.

**Fix:** Cap `amount` in the backend zod schema at a value whose realistic
aggregate cannot overflow (e.g. `.max(100_000_000)`) with a Portuguese message,
and record the cap in `backend.md` §5 and `currency.ts`. The thorough version —
a `BigInt`/`String` scalar for the aggregates — changes a public contract and
touches every display site. Effort: M for the cap, L for the scalar.

### 12. The category token sets are written out three times and nothing compares them

**Evidence:** the same 23 strings appear as zod `as const` arrays
(`backend/src/modules/category/validation.ts:8-35`), as SDL enums in a different
order (`backend/src/modules/category/schema.ts:2-29`), and as a hand-written
frontend union plus array (`frontend/src/lib/category-tokens.ts:24-40,123-150`)
— while the generated union already exists at
`frontend/src/graphql/generated/graphql.ts:8,17` and is not used.
`backend/tests/unit/schema-artifact.test.ts:22` compares SDL against SDL, so it
cannot see the zod list. The frontend's only guard is
`toHaveLength(16)` — a swapped or renamed token passes it.

**Cost:** Add a seventeenth icon to the SDL and forget zod: the schema advertises
it, GraphQL parsing accepts it, and zod answers `BAD_USER_INPUT` with "Selecione
um ícone válido" for a token the schema says is legal — with `test`, `typecheck`
and `codegen:check` all green, because codegen regenerates the artifact from the
wrong half. On the frontend an *added* token is caught by assignability; a
*removed* one is not — `IconPicker` keeps offering a dead token and the user gets
a server rejection.

**Fix:** Backend — interpolate the zod arrays into the SDL template literal, or
add a unit test asserting `CategoryIcon.getValues()` equals `CATEGORY_ICONS`.
Frontend — delete the hand-written unions and re-export the generated ones,
keeping the class-name and label lookups so `Record<CategoryIcon, …>` fails to
compile when the union changes. Effort: M.

### 13. The user-scoping rule is re-implemented at six call sites in three directories

**Evidence:** there is not one `modules/<a>` → `modules/<b>` import — the
boundary looks perfect. At the data layer it is not: `category/service.ts:138`
and `:139-143` query `prisma.transaction`; `transaction/service.ts:22` queries
`prisma.category`; `summary/service.ts:53,58` query `prisma.transaction` and the
module owns no table at all; `shared/dataloaders.ts:33,68` query both.

**Cost:** The definition of done requires every query to filter by the caller in
the `where`. That rule is held at six independent places and correctness depends
on each author remembering. It holds today — all six were read and each carries
`userId`. What it costs is change: adding an `archivedAt` column, a soft delete
or a shared-account concept means finding all six by grep, in three directories,
with no accessor to change once and no lint rule to catch a miss.

**Fix:** Give the loaders' query bodies to the modules that own the tables —
`createLoaders` calls `listCategoryTotals(userId, ids)` and
`findCategoriesByIds(userId, ids)` from `category/service.ts`, and
`assertCategoryOwned` calls `getCategory`. That leaves `summary/service.ts` as
the one deliberate cross-table reader, worth stating in `backend.md` §3 rather
than leaving implied. Effort: M.

### 14. Cache invalidation is re-typed at four sites, `updateCategory` omits two keys

**Merged from `arch-04` and `test-05`.** The architecture agent found the missing
keys; the testing agent found that the update path has no refetch test. Neither
alone is the whole finding: the defect exists *and* the test that would have
caught it is the one missing case.

**Evidence:** `TransactionDialog.tsx:86-103` and `DeleteTransactionDialog.tsx:44-53`
invalidate four keys. `DeleteCategoryDialog.tsx:44-56` invalidates three —
omitting `Summary` correctly, since unlinking moves no money.
`CategoryDialog.tsx:58-66` invalidates only `Categories` and `CategoryStats`; its
comment accounts for a create but not a rename or recolor.
`docs/specs/frontend.md:314` gives the same two, so the code matches the spec and
**the spec is the side that is wrong** — its own reasoning at `:318-320` applies
to a renamed category as much as a deleted one. On the test side,
`CategoriesPage.test.tsx:172,352` assert refetch for create and delete; the two
edit tests (`CategoryDialog.test.tsx:74,100`) assert only mutation variables.
Same shape in `TransactionDialog.test.tsx` — `:135` covers create, `:251` checks
only variables.

**Cost:** Rename or recolor a category, then open `/transactions`: the table
paints from cache with the old tag before the mount refetch replaces it. Because
`staleTime` is 0 (`App.tsx:7-14`) it is a flash, not a permanent state — which is
why this is medium and not high. The structural cost is larger: the contract is
stated once in a spec table and re-typed at four call sites, the four have
already diverged, and no test notices because each dialog asserts its own list.

**Fix:** One helper in `frontend/src/lib/` —
`invalidateAfter(queryClient, 'category' | 'transaction' | 'profile')` — holding
the table from `frontend.md` §6, called by all four dialogs. Add `transactions`
to the category row of the spec table in the same change. Add the two missing
refetch tests, mirroring `CategoriesPage.test.tsx:172-209`. Effort: M.

### 15. The JWT sits in `localStorage` and no CSP narrows the exposure

**Evidence:** `frontend/src/lib/token-storage.ts:9,17` reads and writes
`localStorage`/`sessionStorage` depending on the "Lembrar-me" checkbox; both are
readable by any script on the origin.
`grep -rn "dangerouslySetInnerHTML\|innerHTML\|eval(" frontend/src` — no matches,
so there is no injection sink today. No CSP is set anywhere.

**The tradeoff, stated:** moving to an `httpOnly` cookie is not free. The SPA is
on `:5173` and the API on `:4000` — different origins — so the cookie needs
`SameSite=None; Secure`, which reopens CSRF and needs a double-submit defence. It
also needs a cookie-issuing endpoint, breaks the header path at
`graphql-client.ts:24`, and breaks "Lembrar-me", since an `httpOnly` cookie
cannot be inspected by the script that picks the store. Four files and a contract
change, against an XSS the app has no sink for.

**Cost:** If an XSS is ever introduced — or a compromised dependency runs in the
page — the token is one `getItem` away, and with row 24 it stays valid for seven
days after exfiltration with no way to revoke it.

**Fix:** Do **not** move the token. Serve a `Content-Security-Policy` from
wherever the built frontend is hosted, and do the row 24 revocation work to bound
the damage. Revisit cookies only if both apps end up behind one origin.
Effort: S for the CSP.

### 16. `signUp` is the one create path with no `P2002` catch

**Evidence:** `backend/src/modules/auth/service.ts:25-30` is check-then-create
with no `.catch` on the create, against `email String @unique`. The category
module solves exactly this — `rethrowDuplicateName`
(`category/service.ts:22-31,81,109`) converts `P2002` to `BAD_USER_INPUT` and its
comment spells out the race — and even has tests for it
(`category-service.test.ts:78,121`). `auth.test.ts:78-158` has no equivalent.

**Cost:** Two concurrent sign-ups on one address — a double-clicked submit is
enough — produce `INTERNAL_SERVER_ERROR` instead of the `EMAIL_ALREADY_EXISTS`
the frontend knows how to render, so the user sees a generic failure on a form
that has a specific correct message for their situation. With row 4, Prisma's
message reaches the client verbatim, naming model, operation and column. The race
window is narrow and was not reproduced under load; the missing catch is what is
verified.

**Fix:** Give the auth service the same `P2002` catch, mapping to
`emailAlreadyExists()`. Ideally hoist the shape into `shared/errors.ts` so a
third module does not repeat it. Add the race test. Effort: S.

### 17. `SEED_PASSWORD` bypasses the validated env and sits outside the scanner exemption

**Merged from `sec-09` and `tool-05` — same variable, two symptoms.**

**Evidence:** `backend/prisma/seed.ts:16` —
`process.env.SEED_PASSWORD ?? 'trocar-esta-senha'`. It is the one environment
variable the codebase reads that never passes through `parseEnv`
(`shared/env.ts:3-11` covers five others). `backend/.env.example:8` ships the
literal, and `.gitguardian.yaml:11-14` exempts only the two test-credential
files, its comment claiming a deliberately scoped list that did not account for
this. Nothing stops `npm run seed` running against a non-development
`DATABASE_URL` — the protection is a docstring.

**Cost:** Running the seed against a real database creates `ana@financy.dev` with
a password committed to the repository, and deletes that user's rows on every
run. One command away, and it is an operator mistake rather than an attack. The
`.env.example` literal is a `KEY=literal` pair in a tracked file, exactly the
shape generic-password detectors target — the day scanning joins the gate (row 1)
it either false-positives or gets re-triaged from scratch.

**Fix:** Have `seed.ts` refuse to run when `env.NODE_ENV !== 'development'`, and
either add `SEED_PASSWORD` to `envSchema` as optional with a minimum length or
rename the placeholder to something a scanner skips and a human reads as
non-secret. Effort: S.

### 18. Nothing mechanically enforces the layering both specs describe

**Evidence:** `docs/specs/backend.md:97-106` states resolvers "contain no
business rules and never call Prisma directly". `eslint.config.mjs:25-32` carries
only `no-undef` off, `no-explicit-any` and `no-unused-vars` — no
`no-restricted-paths`, no boundary plugin. The rules hold today, verified:
`grep -rn 'prisma' backend/src/modules --include=resolvers.ts` → no matches, and
nothing under `frontend/src/lib/` imports from `features/` or `components/`. The
one inversion that exists is deliberate and spec'd — the layout guards import
`@/features/auth/useSession`, which `frontend.md:405` puts there.

**Cost:** Forward-looking. Four invariants the specs state are held by author

reading. The concrete one to guard: resolvers already import from `shared/`, so

### 19. Registering a module is five hand edits, and skipping one passes every check

### 22. Nothing asserts DataLoaders are rebuilt per request

### 24. Tokens live seven days with no revocation and no `iss`/`aud`

**Evidence:** `backend/src/shared/jwt.ts:8-15` — `signToken` sets only `sub`,
`iat` and a 7-day expiry; no `iss`, `aud` or `jti`. Verification pins the
algorithm (`:20-22`), so `alg: none` and confusion are closed, but neither issuer
nor audience is checked because neither is set. There is no `signOut` mutation
anywhere. `frontend/src/features/auth/SessionContext.tsx:39-40` — sign-out is

`User` has no `tokenVersion` column for `createContext` to check.

**Cost:** A token copied off a shared machine keeps working for up to seven days

everybody out at once.

**Fix:** An integer `tokenVersion` on `User`, carried in the claims and compared

`iss`/`aud` at the same time. Touches `schema.prisma` plus a migration, `jwt.ts`,
`context.ts`, the auth module and the frontend `SessionContext`. Effort: L.
